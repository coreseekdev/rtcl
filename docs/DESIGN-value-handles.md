# 设计：`Value` 字符串句柄共享（TODO 5 号）

状态：设计稿（2026-10-18）。本文只描述**方案与分期**，不改 `Value` 表示（仓库无 intern 表）。

## 1. 为什么做（已有实证）

Round AA 的 OO 派发站点缓存（`OoCallCache`，`04fd3ed`）之所以能命中，前提是
**常量池字面量的 `Value` 分配在热点循环里稳定**：`c compute 7 3` 里 `"c"`、
`"compute"` 每次都是同一个 `ValueInner`，于是 `Value::same_allocation` 的
分配同一性比较（bits 相等——立即数为值等价、堆值为同 box）可作廉价的「同一性」验证（再叠加 ns 指针 + `mutation_ctr` 保证语义）。

这一机制在**计算出的名字**上立刻失效，Round AB 的 `my` 实验就是反例：
`my a`/`my b` 交替时单槽缓存被冲刷（−2.89% 回退），而若名字来自变量或拼接
（`$o $m`、`my $method`），每次都是新分配，identity 检查永不命中。

目标：给「名字类字符串」一个**线程内驻留（intern）**，使相同文本在任意构造点
都指向同一 `ValueInner`。收益是全局性的：

- 派发站点缓存从「字面量站点」推广到「变量/计算名站点」（`my`、`$o $m`）；
- 变量名、命名空间名、命令名的查找可用 ptr 快筛（`objects.get(name)` 前的
  短路、`chain_memo` 探测的键比较）；
- 与 3 号的**复利**：缓存层不需要多槽哈希/预测器，直接 identity 命中。

## 1.5 实测修订（2026-10-18，Round AA/AG）

实现派发站点缓存的过程中，S1 的预期收益被**提前兑现**且不需要驻留表：

- 对象派发（Round AA 单槽 → AG 单槽确认）：字面量与变量名（`$o $m`）都
  已是稳定分配（常量池/槽 clone），`dispatch_dynamic` 与字面量同速
  （4.448G，1M 次调用）✓。
- `my` 派发（Round AG 双槽）：a↔b 交替递归 **−32.3%**（17.466G→11.827G）；
  双槽按「方法词身份」共存，交替名不再冲刷。
- 因此 **S1（名字构造点显式共享）不再需要**：派发链的身份命中已由
  `OoCallCache` + 双槽覆盖；`qualify`/`chain_memo`/`key_memo` 仍是文本
  哈希（每次 1-2 次探测，已足够便宜，实测无热点）。

剩余价值只在**拼出来的名字**（`$o [string cat ...]`、命令名拼接）：每次
都是新分配 → 身份缓存必 miss（语义正确，只是退回哈希路径）。若 S2
（短串驻留在 `Value` 构造点）落地，这类站点可提为身份命中；代价是每个
短串构造多一次哈希查找，**必须在 micro_add/lappend（数据串密集）上先
证明无回退**，且板面六个基准都不覆盖该路径（收益是长尾的）。故列为
「有证据再动」。

## 1.6 结论（2026-10-18，本条目的收口判定）

- **S1 不做**：预期收益已被 Round AA/AG 的派发缓存提前兑现（见 1.5 的实测）。
- **S2 评估后不做（有证据）**：S2 的唯一增量场景是「拼出来的名字」被反复
  派发（`$o [string cat ...]`）。该场景现状 = `key_memo`(1 哈希) +
  `chain_for`(2 哈希) ≈ 60-90 instr/调用，且语义正确；S2 若要把它抬成身份
  命中，代价是**每一次短串构造**多一次哈希查找——命中收益只落在罕见站点，
  成本落在所有短串（数据串密集的 micro_add/lappend、dict 键等）。板面六个
  基准均不覆盖该路径（收益为长尾），故按设计红线「不得吞性能」判定不做。
- **S3 不做**（原计划即如此）。
- 保留的红线/契约条款（第 2、4 节）继续作为未来任何驻留方案的准入标准。

## 2. 红线（不可越）

1. **语义不变**：驻留只影响分配布局，绝不改变任何比较/求值结果。所有基于
   identity 的捷径必须仍然带语义验证（stamp / ns 指针 / 归属表检查），
   即「identity ⟹ 相等」的**单向**推理，不得反向（不得用 identity 代替
   `==` 去实现应该按文本比较的地方）。
2. **不得泄漏**：驻留表持 `Weak`；被驻留字符串的全部分配随最后一个强引用
   消失。表有条数上界 + 溢出策略（清空或 LRU 段淘汰），wasm32 上界更小。
3. **不得吞性能**：只驻留「名字类」短串（下述），数据串（dict 值、列表元素、
   `puts` 内容、字符串拼接结果）不进表——它们是长尾且构造频繁。
4. **可关**：feature/配置可关闭驻留，便于 A/B 与 JIT 侧对齐。

## 3. 分期

### S1（低风险，建议先做）：名字构造点显式共享

不改 `Value` 表示，只在**已知是名字的构造点**做「同一化」：

- `qualify()` / `normalise()` / `resolve_command_key()` 的输出：走一个
  `interp.name_intern: FxMapK<Rc<str>, Weak<str>>`（或反过来查一份
  `Rc<str>` 强表），命中即 clone `Rc`，未命中插入。
- `my_commands` 键、`chain_memo` 外层键、方法名的 `Rc<str>`
  （`chain_for` 的 `method_rc` 已共享）统一从该表取。
- `cmd_oo_object`/`cmd_oo_my` 缓存扩展为 **2-4 槽、按 (typed, method) 双
  身份键控**——S1 之后，变量/计算名也能稳定命中，Round AB 的冲刷问题消失。

验收：`/tmp/my_bench.tcl`（a↔b 交替递归）A/B 必须转正；`$o $m` 形状的
新建微基准应有同量级收益；六板不动即算成功（该路径板面不覆盖）。

### S2（中风险）：短串全局驻留

线程本地（`thread_local!`，与 `Value::empty()` 单例同范式）：
`Weak<str>` 表 + 长度门（≤ 32B）+ 字符集门（无空白/非数字开头，近似标识符）
+ 上界（如 4096 条，超限清半）。`Value::from_str` 的短名字路径先查表。
风险：每个短串构造多一次哈希查找；须用 micro_add/lappend（数据串密集）
证明无回退，再谈收益。

### S3（高风险，暂不计划）：表示层统一

把「已驻留短串」的 `ValueInner` 字符串表示换成全局 `Rc<str>` 引用计数
共享（去掉每值 Rc 独立分配），涉及 `Value` 布局、`same_allocation` 语义
在 imm/共享两态的区分、JIT 侧对接——只有在 S1+S2 的收益 ≥5% 且稳定后才评估。

## 4. 与 JIT 的契约

驻留表是解释器内部缓存，不改变 `ByteCode`/`unfused()` 边界；但
`same_allocation` 的语义若在 S3 变化，必须在
`docs/JIT-OPCODE-DELTA.md` 顶部追加一节说明（当前：identity 仅用于解释器
内部 memo 验证，JIT 不依赖）。

## 5. 度量与回归

- 微基准：`my_bench`（交替名）、新建 `dispatch_dynamic.tcl`（`$o $m`）、
  `dispatch_literal.tcl`（现状保护，不得回退）。
- 六板：oo2/oovars 不得回退；fib/dloop/fe/build 持平。
- 四道门照旧（tests/judge/sweep + 指令数）。
- 每期单独提交；无板面/微基准正收益即回退并记入 `bench/BASELINE.md`。
